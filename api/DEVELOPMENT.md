# تطوير الواجهة البرمجية

Worker على كلاودفلير بـ Hono وD1. كل الأوامر من داخل `api/`.

```sh
npm install        # npm 11 أو أحدث؛ npm 10 يتعطّل مع vitest 5
npm test           # الاختبارات داخل بيئة Workers الحقيقية (Miniflare) مع D1 محلية
npm run typecheck
npm run dev        # خادم محلي على http://localhost:8787
npm run db:migrate:local
```

## الهيكل

| الملف | ما فيه |
| --- | --- |
| `migrations/` | مخطط قاعدة البيانات D1، ملف لكل تغيير ولا يُعدَّل ملف بعد نشره |
| `src/auth/` | التحقق من رمز Sign in with Apple (`apple.ts`) ورمز Google (`google.ts`)، وربط الحسابات بالمستخدمين ودمجها بالبريد (`users.ts`)، وجلسات الخادم (يُحفظ تجزيء الرمز فقط)، ورمز Apple الذي يُلغى عند حذف الحساب (`apple-tokens.ts`) |
| `src/data/schemas.ts` | شكل كل كيان وقيوده (zod) |
| `src/data/mutations.ts` | كل كتابة تمر من هنا: الصلاحيات، والأحدث يفوز، وسجل التغييرات |
| `src/data/pull.ts` | ما تغيّر للمستخدم منذ مؤشر معيّن |
| `src/data/membership.ts` | إضافة الأعضاء وإزالتهم وما يلزم مزامنتهم |
| `src/data/account.ts` | حذف الحساب وبياناته |
| `src/routes/` | المسارات |
| `src/push/` | إشعارات الخادم: تسجيل الأجهزة، ومرسل APNs، ومهمة الـ Cron |
| `src/realtime/` | المزامنة اللحظية: كائن `UserChannel` لكل مستخدم، وتذاكر المتصفح، ومن يُنبَّه بعد كل كتابة |
| `src/imports/` | الاستيراد من التطبيقات الأخرى: المصادر، والطابور، والكتابة عبر الـ Mutator |

## المزامنة

التطبيق يعمل دون اتصال، ويتزامن بطلبين:

- `POST /v1/sync` يرسل التعديلات المحلية `{ mutations: [{ op: "upsert", entity, data } | { op: "delete", entity, id, updatedAt }] }`، وتُطبَّق بالترتيب، ولكل واحدة نتيجتها: `applied` أو `stale` (عند الخادم نسخة أحدث) أو `gone` (محذوفة) أو `forbidden` أو `invalid`.
- `GET /v1/sync?cursor=N` يرجع آخر حالة لكل سجل تغيّر بعد المؤشر، أو `delete` إن حُذف أو لم يعد ظاهراً للمستخدم، ثم المؤشر الجديد. يحفظ التطبيق المؤشر ويكرر الطلب ما دام `hasMore` صحيحاً.

الكيانات: `project` و`section` (أعمدة الكانبان) و`task` و`reminder` و`comment`. المعرّفات UUID يولّدها التطبيق، و`updatedAt` بالملّي ثانية من وقت التعديل على الجهاز، والأحدث يفوز.

- مهمة بلا مشروع في صندوق صاحبها وحده. مهام المشروع يراها كل أعضائه، ويعدّلها المالك والمحرر.
- التذكيرات شخصية: كل عضو في مشروع مشترك يضع تذكيراته ولا يراها غيره.
- موعد المهمة تاريخ ميلادي محلي (`dueDate`)، والهجري يُحسب في التطبيق بتقويم أم القرى. أو تُربط بصلاة: `duePrayer` و`duePrayerOffset` بالدقائق.
- نقل مهمة بين المشاريع ينقل مهامها الفرعية، ويُبلَّغ أعضاء المشروع القديم بحذفها من عندهم.

## المشاركة

الأدوار: المالك والمحرر يعدّلان، والمشاهد يقرأ ويعلّق، والمالك وحده يحذف المشروع ويدعو ويغيّر الأدوار ويزيل الأعضاء.

- الدعوة رابط `https://zimam-web.fahad2ao.workers.dev/join/#<code>` (لاحقاً `https://zimam.app/join/#<code>`)، والرمز بعد `#` فلا يصل إلى سجلات الخادم. يفتح صفحة الانضمام في الموقع، أو التطبيق مباشرة إن كان مثبتاً (الروابط العامة، `docs/setup.md`). يُستعمل مرة واحدة وينتهي بعد ٧ أيام. يُحفظ تجزيء الرمز فقط في جدول `invites`، فلا يظهر الرمز بعد إنشائه. ولكل دعوة معرّف `id` يرى به المالك دعواته ويلغي منها ما لم يُستعمل.
- من يقبل دعوة وهو عضو يبقى على الأعلى من دوره ودور الدعوة، ولا تُستهلك الدعوة إلا إذا رفعت دوره.
- المجلدات لا تُشارَك، لأن مشاركة المجلد لا تشارك المشاريع التي فيه.

العضو الجديد مؤشره تجاوز سجلات المشروع القديمة، والعضو المُزال لا تصله تغييرات المشروع بعد خروجه. لذلك يُضاف عند القبول وعند الإزالة سجل تغيير موجّه للمستخدم نفسه (`user_id`) لكل ما هو حي في المشروع: المشروع وأعمدته ومهامه وتعليقاتها. وطلب `GET /v1/sync` يتحقق من الظهور عند السحب، فتصل للعضو الجديد كاملة، وتصل للمُزال حذفاً. وعند الإزالة أيضاً تُلغى إسناداته في المشروع، وتُحذف تذكيراته على مهامه.

## الواجهة البرمجية للموقع وخادم MCP

| المسار | ما يفعله |
| --- | --- |
| `POST /v1/auth/apple` | `{ identityToken, nonce?, name?, device?, authorizationCode? }` يرجع `{ token, user }` |
| `POST /v1/auth/google` | `{ idToken, nonce?, name?, device? }` يرجع `{ token, user }` كذلك، و503 `google_unavailable` إن كان `GOOGLE_CLIENT_IDS` فارغاً (انظر «تسجيل الدخول») |
| `POST /v1/auth/logout` | ينهي الجلسة |
| `GET`, `PATCH`, `DELETE /v1/me` | الحساب والإعدادات (`calendar`، `prayerMethod`، `weekStart`، `timeZone`، `location`)، والحذف يمسح بيانات المستخدم (انظر «حذف الحساب») ويرجع 204 |
| `GET`, `POST /v1/projects` | المشاريع مع عدد المهام والمنجز منها |
| `GET`, `PATCH`, `DELETE /v1/projects/:id` | المشروع وأعمدته |
| `GET /v1/tasks` | تصفية بـ `projectId` (أو `inbox`) و`status` (أو `open`) و`dueFrom` و`dueTo` و`q` و`assignee=me` |
| `POST /v1/tasks`، `GET`, `PATCH`, `DELETE /v1/tasks/:id` | المهمة |
| `POST /v1/tasks/:id/complete` | إنجاز مهمة |
| `GET /v1/projects/:id/members` | الأعضاء `{ members: [{ userId, name, role, addedAt }] }`، لكل عضو |
| `PATCH /v1/projects/:id/members/:userId` | `{ role: "editor" \| "viewer" }`، للمالك، ولا يتغيّر دور المالك |
| `DELETE /v1/projects/:id/members/:userId` | المالك يزيل عضواً، أو العضو يغادر. المالك لا يغادر (`owner_cannot_leave`) |
| `GET`, `POST /v1/projects/:id/invites` | للمالك: الدعوات السارية دون رموزها `{ invites: [{ id, role, createdBy, createdAt, expiresAt }] }`، وإنشاء دعوة `{ role }` ترجع `{ id, code, url, expiresAt }` |
| `DELETE /v1/projects/:id/invites/:inviteId` | للمالك: إلغاء دعوة قبل استعمالها (204، وإلغاؤها مرتين لا يضر)، و410 `invite_used` إن قُبلت |
| `GET /v1/invites/:code` | معاينة الدعوة `{ projectName, role, invitedBy, expiresAt }`، و410 إن انتهت أو استُعملت أو أُلغيت (`invite_expired`، `invite_used`، `invite_revoked`) |
| `POST /v1/invites/:code/accept` | الانضمام إلى المشروع، يرجع `{ projectId, role }` |
| `GET`, `POST /v1/tasks/:id/comments` | تعليقات المهمة من الأقدم مع `authorName`، وإضافة تعليق `{ body }` |
| `DELETE /v1/comments/:id` | حذف تعليق، لكاتبه فقط |

كل المسارات بعد تسجيل الدخول تحتاج `Authorization: Bearer <token>`. الأخطاء بالشكل `{ error: { code, message } }`؛ الرمز ثابت بالإنجليزية، والتطبيق يعرض نصه العربي.

البحث `q` يتجاهل التشكيل والتطويل، ويوحّد الألف والتاء المربوطة والألف المقصورة، ويطابق الأرقام الهندية بالعربية.

## واجهة المساعدات (خادم MCP)

خادم MCP في `mcp/` لا يصل إلى قاعدة البيانات، بل يستدعي هذا الـ Worker عبر Service Binding إلى الصنف `ZimamService` (`src/service.ts`). هذا المدخل لا يُفتح من الإنترنت، ويأخذ معرّف المستخدم من منحة OAuth التي تحقق منها خادم MCP.

المنطق في `src/assistant.ts`، وإجاباته مهيّأة للنماذج اللغوية: الأولوية بالاسم، والتاريخ بالهجري والميلادي، ووقت الصلاة بالكلمات («بعد المغرب بـ٢٠ د»).

| الطريقة | ما تفعله |
| --- | --- |
| `signInWithApple(identityToken, nonce)` | تتحقق من رمز Apple الصادر للويب (`app.zimam.ios.web`) وترجع مستخدم زمام |
| `signInWithGoogle(idToken, nonce)` | تتحقق من رمز Google الصادر لعميل الويب، وترجع مستخدم زمام بقاعدة الدمج نفسها، و`google_unavailable` إن لم يُضبط Google |
| `listTasks`، `createTask`، `updateTask`، `completeTask` | المهام بنفس صلاحيات التطبيق وسجل المزامنة |
| `listProjects` | المشاريع مع الدور وعدد المهام |
| `getAgenda({ from?, days? })` | الأيام بالتقويمين، وأوقات الصلاة إن حفظ المستخدم موقعه، ومهام كل يوم، والمتأخرة |

يحسب الخادم «اليوم» بالمنطقة الزمنية في إعدادات المستخدم (`timeZone`، والافتراضي `Asia/Riyadh`)، وأوقات الصلاة بمكتبة `adhan` من `location` وطريقة الحساب. ويرسلهما التطبيق عبر `PATCH /v1/me` حين يسمح المستخدم بالموقع.

## تسجيل الدخول

يدخل المستخدم بحساب Apple أو Google، ولكلٍّ منهما سطر في جدول `identities` (`migrations/0008_identities.sql`): المزوّد (`apple` أو `google`) ومعرّف الحساب عنده (`sub`) والمستخدم والبريد وهل تحقق منه المزوّد. للمستخدم الواحد حسابان أو أكثر، ويُعرف عند كل دخول بالمزوّد والمعرّف فقط.

- **Apple:** يتحقق الخادم من توقيع Apple والمصدر `https://appleid.apple.com` والجمهور (`APPLE_AUDIENCES`) والصلاحية، ومن الـ nonce إن أُرسل.
- **Google:** يتحقق من توقيع Google بمفاتيح `https://www.googleapis.com/oauth2/v3/certs`، والمصدر `accounts.google.com` أو `https://accounts.google.com`، والجمهور (أحد معرّفات `GOOGLE_CLIENT_IDS`: عميل iOS ثم عميل الويب)، والصلاحية. وإن أرسل العميل `nonce` وجب أن يحمل الرمز تجزئته SHA-256 بالست عشري، كما في Apple. معرّفات العملاء ليست أسراراً، وهي في `wrangler.jsonc`؛ وإن فرغ المتغير رجع `/v1/auth/google` بـ 503 `google_unavailable`.
- مفاتيح المزوّدَين تمر عبر `Deps.appleKeys` و`Deps.googleKeys`، فتوقّع الاختبارات رموزها بمفاتيح محلية (`test/helpers.ts`)، وتعمل بمعرّفات عملاء للاختبار يضبطها `vitest.config.ts`. و`ZimamService.keys` كذلك لخادم MCP.
- الاسم يُحفظ من أول دخول أعطاه (Apple يرسله مرة واحدة)، وبريد الحساب يتبع الحساب الذي جاء منه.
- العمود القديم `users.apple_sub` باقٍ لأن حذف قيده يتطلب إعادة بناء الجدول: فيه معرّف Apple لمن بدأ حسابه بـ Apple، و`none:<id>` لمن بدأ بـ Google، و`deleted:<id>` بعد الحذف. الدخول يقرأ `identities`، ولا يقرأ `apple_sub` إلا ليتبنّى مستخدماً أنشأه الكود القديم قبل أن يُنشأ سطره في `identities` (بين تطبيق الترحيل والنشر).

### دمج الحسابات بالبريد المتحقَّق منه

قرار المالك: تُدمج الحسابات تلقائياً بالبريد المتحقَّق منه، فمن دخل التطبيق بـ Apple ثم الويب بـ Google وجد مهامه نفسها. القاعدة في `signInUser` (`src/auth/users.ts`):

1. الحساب المعروف (المزوّد والمعرّف في `identities`) يدخل مستخدمه دائماً، ولا يُنقل إلى غيره ولو تغيّر بريده لاحقاً.
2. أول دخول لحساب جديد يُضمّ إلى مستخدم موجود فقط إذا: تحقق المزوّد من البريد في الرمز (`email_verified`)، وكان لمستخدم **واحد فقط** حساب (من أي مزوّد) بالبريد نفسه متحقَّقاً منه، دون اعتبار لحالة الأحرف.
3. عناوين Apple الخاصة (`@privaterelay.appleid.com`) لا يُطابق عليها أبداً.
4. غير ذلك (لا بريد، أو غير متحقَّق منه، أو عنوان خاص، أو لا مستخدم، أو أكثر من مستخدم) يبدأ مستخدماً جديداً.

القاعدة نفسها لـ Apple وGoogle، وفي التطبيق والويب وخادم MCP. والحسابات التي سبقت هذا الترحيل نُقلت إلى `identities` حسابات Apple ببريدها متحقَّقاً منه، لأن Apple لا يعطي إلا بريداً تحقق منه.

لماذا هذه القاعدة آمنة بما يكفي، وما حدودها:

- **الدمج يعطي الداخل الجديد كل بيانات الحساب القديم.** فلا يُدمج إلا على بريد يشهد مزوّدُه أنه تحقق من ملكيته، من الطرفين: البريد غير المتحقَّق منه يستطيع أي أحد كتابته، فلو قُبل لأمكن الاستيلاء على حساب غيرك بإنشاء حساب Google باسم بريده.
- **لا تخمين:** إن وُجد أكثر من مستخدم بالبريد نفسه بدأ حساباً جديداً بدل أن يختار أحدهم.
- **العنوان الخاص من Apple** عنوان تحويل خاص بزمام، لا يثبت هوية في مكان آخر، فلا يُطابق عليه.
- **الدمج عند أول دخول للحساب الجديد فقط:** الحساب المربوط لا ينتقل بعدها، فتغيير البريد لا يحرّك الحسابات بين المستخدمين.
- **متى يُعدّ بريد Google موثّقاً للدمج:** `email_verified` وحده لا يكفي، لأن Google تتحقق من البريد الخارجي مرة واحدة عند إضافته وقد تزول ملكيته لاحقاً (نطاق انتهى أو موظف غادر). فلا يُدمج من Google إلا بريد `gmail.com` (أو `googlemail.com`) أو حساب Google Workspace (فيه ادعاء `hd`)، وهي التوصية الرسمية من Google. غير ذلك يدخل بحساب مستقل (`verifyGoogleToken` في `src/auth/google.ts`).
- **لا فصل بعد الدمج:** لا واجهة لفصل حسابين مدموجين؛ حذف الحساب يحذف ربط الحسابين معاً.
- **خادم MCP:** صفحة الموافقة تطلب من Apple بلا نطاقات (لا بريد في الرمز)، فإن ربط المستخدم MCP بحساب Apple لم يدخل به التطبيق قط ولا بريد في رمزه بدأ حساباً جديداً. الأفضل أن يختار في صفحة الموافقة الحساب نفسه الذي يستعمله في التطبيق.

## المساعد الذكي داخل التطبيق

ثلاثة مسارات بعد تسجيل الدخول، لا تحفظ شيئاً: يعرض التطبيق الاقتراح ويؤكده المستخدم ثم يحفظه بالمزامنة كالعادة.

| المسار | ما يفعله |
| --- | --- |
| `POST /v1/assistant/parse` | `{ text, now? }` يحوّل جملة («ذكرني أراجع العقد بعد المغرب يوم الخميس») إلى اقتراح مهمة `{ title, notes?, dueDate?, dueTime?, duePrayer?, duePrayerOffset?, priority, tags, projectId? }` |
| `POST /v1/assistant/breakdown` | `{ taskId }` يرجع `{ subtasks }` من ٣ إلى ٨ عناوين قصيرة لمهمة يراها المستخدم، و404 لغيرها |
| `GET /v1/assistant/summary?date=` | `{ date, text }` ملخص صباحي من بيانات `getAgenda` وحدها: مهام اليوم والمتأخرة وأقرب مهمة مرتبطة بصلاة. اليوم الفارغ يُجاب دون النموذج ودون احتساب |

- `now` وقت الجهاز (ISO مع المنطقة)، والافتراضي وقت الخادم. «اليوم» بمنطقة المستخدم (`timeZone`، والافتراضي `Asia/Riyadh`).
- يُعطى النموذج اليوم بالتقويمين، وجدول الأيام الأربعة عشر القادمة بأسمائها وبالهجري، وأسماء المشاريع التي يستطيع المستخدم الإضافة إليها. التاريخ الهجري في الجملة («١٥ رمضان») يرجعه النموذج أجزاءً ويحوّله الخادم بتقويم أم القرى (`dayOfHijri` في `src/data/dates.ts`)، فلا يحسب النموذج التقويم.
- جواب النموذج غير موثوق: يُتحقق منه بـ zod بقواعد `TaskFields` نفسها، وتُزال الرموز التعبيرية والتطويل، ويُحذف `projectId` إن لم يكن من مشاريع المستخدم، ويُقدَّم الربط بالصلاة على الوقت إن جاء الاثنان.
- الأخطاء: `400 invalid` لمدخل خاطئ، و`429 ai_quota_exceeded` مع `limit` و`resetsOn` (أول الشهر القادم)، و`503 ai_unavailable` إن فشل المزوّد أو رفض أو رجع جواباً لا يصلح. الفشل لا يُحتسب من الحصة.

الملفات: `src/ai/provider.ts` (واجهة `AiProvider` وتنفيذا Anthropic وDeepSeek)، و`src/ai/prompts.ts` (التعليمات)، و`src/ai/validate.ts` (فحص الأجوبة)، و`src/ai/quota.ts`، و`src/routes/assistant.ts`. المزوّد يُمرَّر عبر `Deps.ai` فتستعمل الاختبارات مزوّداً وهمياً (`FakeAi` في `test/helpers.ts`).

### المزوّد والنموذج

- `AI_PROVIDER = "anthropic"`: نموذج `claude-haiku-5-5` (أرخص نماذج كلود الحالية، وجيد في العربية)، بمخرجات منظّمة (`output_config.format` بمخطط JSON) وجهد `low`.
- `AI_PROVIDER = "deepseek"`: نموذج `deepseek-chat` بوضع JSON (`response_format: { type: "json_object" }`)، والمخطط في رسالة النظام.
- `AI_MODEL` (اختياري) يغيّر النموذج دون تغيير الكود.

كل الطلبات تمر عبر Cloudflare AI Gateway، والمفتاح في الترويسة لا في الرابط.

### الحصة

`AI_MONTHLY_LIMIT` طلباً لكل مستخدم في الشهر الميلادي بتوقيت UTC (الافتراضي ٣٠٠). الجدول `ai_usage` يحفظ لكل مستخدم وشهر عدد الطلبات والرموز الداخلة والخارجة، لا النصوص. الفحص قبل الطلب والتسجيل بعد نجاحه، فطلبان متزامنان عند الحد قد يتجاوزانه بواحد.

### الإعداد

القيم غير السرية في `wrangler.jsonc` (`vars`): `AI_PROVIDER` و`AI_GATEWAY_URL` و`AI_MONTHLY_LIMIT`. المفاتيح أسرار فقط، ولا تدخل المستودع ولا التطبيق:

1. في لوحة كلاودفلير: **AI → AI Gateway → Create Gateway** باسم `zimam` في الحساب `302d00b357e2c90ed474d13642708b30`. الرابط حينها `https://gateway.ai.cloudflare.com/v1/302d00b357e2c90ed474d13642708b30/zimam`، ويضيف الخادم إليه `/anthropic/v1/messages` أو `/deepseek/chat/completions`.
2. يُستحسن تفعيل السجلات وحدّ المعدل في البوابة. وإن فُعّلت **Authenticated Gateway** فأنشئ رمزاً وأضفه سراً (`AI_GATEWAY_TOKEN`)، ويُرسل في `cf-aig-authorization: Bearer …`.
3. أضف المفاتيح من داخل `api/`:

```sh
npx wrangler secret put ANTHROPIC_API_KEY
npx wrangler secret put DEEPSEEK_API_KEY    # عند استعمال DeepSeek
npx wrangler secret put AI_GATEWAY_TOKEN    # للبوابة الموثّقة فقط
npx wrangler d1 migrations apply zimam --remote   # جدول ai_usage
```

للتبديل إلى DeepSeek غيّر `AI_PROVIDER` في `wrangler.jsonc` إلى `"deepseek"` وانشر. وللتطوير المحلي ضع المفاتيح في `api/.dev.vars` (لا يُرفع إلى المستودع).

## حذف الحساب

`DELETE /v1/me` يحذف الحساب كما تشترط مراجعة App Store (البند 5.1.1(v))، والمنطق في `src/data/account.ts`:

- **المشروع الذي يملكه وحده** يُحذف بأعمدته ومهامه وتذكيراتها، كما يحذفه مالكه. والمجلد كذلك، وتخرج المشاريع التي فيه إلى المستوى الأعلى.
- **المشروع المشترك الذي يملكه** ينتقل إلى أقدم أعضائه انضماماً (`added_at`، ثم معرّف المستخدم عند التساوي) أياً كان دوره، فيصير مالكه، ولا يضيع عمل الآخرين. ثم يخرج منه المالك السابق كأي عضو مُزال، ويُسجَّل تغيير للمشروع فيصل المالك الجديد إلى أجهزة الأعضاء.
- **المشاريع التي هو عضو فيها** يخرج منها بـ `removeMemberStatements` نفسها: تُلغى إسناداته، وتُحذف تذكيراته، ويُضاف سجل التغيير الموجّه له. المهام التي أنشأها فيها تبقى للمشروع.
- مهام صندوقه وتذكيراته كلها وتعليقاته في كل مكان تُحذف، مع سجل تغيير لجمهور كل سجل، فتحذفها أجهزة من يراها.
- الدعوات التي أنشأها ولم تُستعمل تُلغى، وكل جلساته تنتهي، فلا تعمل رموزه على أي جهاز.
- الحذف ناعم (`deleted_at`) لتعرف المزامنة به، لكن نصوص السجلات المحذوفة تُمسح (العنوان والملاحظات والوسوم والاسم ونص التعليق والموقع). وسطر المستخدم يبقى مجهول الهوية (`apple_sub = 'deleted:<id>'` دون اسم ولا بريد)، لأن سجلات أخرى تشير إليه. وتُحذف كل حساباته في `identities` (Apple وGoogle)، فإن سجّل الدخول بأحدها بدأ حساباً جديداً فارغاً.
- الجلسات تُحذف في آخر خطوة، فإن فشل الحذف في منتصفه بقي المستخدم مسجّلاً ليعيد المحاولة، وكل خطوة تتجاوز ما أُنجز قبلها.

### رمز Sign in with Apple

يرسل التطبيق عند الدخول `authorizationCode` الذي يعطيه Apple. يستبدله الخادم من `https://appleid.apple.com/auth/token` برمز تحديث (`refresh_token`)، ويحفظه في سطر المستخدم (`apple_refresh_token`) مع المعرّف الذي صدر له رمز الهوية (`apple_client_id`: `app.zimam.ios` للتطبيق أو `app.zimam.ios.web` للويب). ويتحقق أن الرمز للمستخدم نفسه (`sub`). وعند حذف الحساب يُلغى من `https://appleid.apple.com/auth/revoke` ويُمسح.

- `client_secret` رمز JWT بـ ES256 يوقّعه الخادم بمفتاح Sign in with Apple عند كل طلب: `iss` معرّف الفريق، و`sub` معرّف العميل، و`aud` `https://appleid.apple.com`، وصلاحيته خمس دقائق.
- معرّف الفريق `APPLE_TEAM_ID` ليس سراً، وهو في `wrangler.jsonc`. معرّف المفتاح `APPLE_KEY_ID` والمفتاح نفسه `APPLE_PRIVATE_KEY` (نص ملف `.p8`) سرّان فقط، وطريقة إنشائهما في `docs/setup.md`.
- إن غاب السرّان، أو رفض Apple الرمز، يتم الدخول والحذف كالعادة، ويُكتب السبب في السجل دون الرمز. الاستبدال والإلغاء يمرّان عبر `Deps.appleTokens`، فتستعمل الاختبارات `FakeAppleTokens` في `test/helpers.ts`.
- يُحفظ رمز آخر دخول فقط. من دخل من التطبيق والويب معاً يُلغى عند الحذف رمز آخرهما، وإلغاؤه يُنهي ربط زمام بحساب Apple.

## إشعارات الخادم (APNs)

يسمح iOS بـ ٦٤ إشعاراً محلياً معلّقاً، فيجدول التطبيق بعد كل سحب للمزامنة ما يقع في الأيام الأربعة عشر القادمة (`ReminderPlanner.windowDays`، بحد ٦٠ إشعاراً). وما بعد ذلك يرسله الخادم عبر APNs.

### تسجيل الجهاز

| المسار | ما يفعله |
| --- | --- |
| `PUT /v1/devices/:token` | `{ platform: "ios" \| "macos" \| "watchos", environment: "sandbox" \| "production", bundleId }` يسجّل رمز APNs (ست عشري) للمستخدم وللجلسة الحالية، ويرجع 204 |
| `DELETE /v1/devices/:token` | يحذف الرمز، لصاحبه فقط (404 لغيره). يستدعيه التطبيق قبل تسجيل الخروج |

- الجهاز مربوط بالجلسة: تسجيل الخروج أو حذف الحساب يحذف الجلسة فيُحذف الجهاز معها (`ON DELETE CASCADE`).
- الرمز المسجَّل لحساب آخر ينتقل إلى من سجّله (التثبيت نفسه دخل بحساب آخر). والرمز الأقدم للجلسة والمنصة نفسيهما يُحذف، لأن APNs أعطى التثبيت رمزاً جديداً.
- `last_seen_at` آخر سحب للمزامنة (`GET /v1/sync`) من جلسة الجهاز، ويُكتب قبل قراءة التغييرات. التسجيل وحده لا يُعدّ سحباً: الجهاز الجديد أو المنقول يبدأ بصفر، والجلسة نفسها تحتفظ بقيمتها.

### القاعدة: متى يرسل الخادم

كل ٥ دقائق (`triggers.crons` في `wrangler.jsonc`، والدالة `scheduled` في `src/index.ts`) يبحث الخادم عن التذكيرات التي حان وقتها في النافذة (الآن − ٥ د، الآن]، ويرسل التذكير الذي وقته F للمستخدم U إذا لم يكن لـ U جهاز:

```
last_seen_at >= max(F − 14 يوماً, وقت آخر تعديل للتذكير)
```

- الجهاز الذي سحب في T جدول محلياً كل تذكير يعرفه في (T، T + ١٤ يوماً]، فلا يُرسل الخادم ما غطّاه، ولا يتكرر الإشعار.
- وقت التعديل `updated_at` للتذكير (ومعه `updated_at` للمهمة في تذكيرات الصلاة، لأن يوم الاستحقاق يحدد الوقت). فالتذكير المضاف من الويب أو من كلود بعد آخر سحب للجهاز يُرسل من الخادم وإن كان الجهاز نشطاً.
- يكفي جهاز واحد مغطٍّ ليتركه الخادم للأجهزة، وإذا أرسل فإلى كل أجهزة المستخدم.
- ما يُحسب كما يحسبه التطبيق: تذكير الوقت في `at` (بالثانية)، وتذكير الصلاة والمهمة المرتبطة بصلاة عند الصلاة مع الإزاحة يوم الاستحقاق، أو كل يوم إن لم يكن للمهمة تاريخ. المهمة المنجزة أو المحذوفة لا تُذكَّر. والمهمة المرتبطة بصلاة في مشروع مشترك تصل لكل أعضائه، كما يجدولها التطبيق على جهاز كل عضو.
- أوقات الصلاة من `location` و`timeZone` وطريقة الحساب في إعدادات المستخدم (`prayerInstants` في `src/data/prayers.ts`). من لم يحفظ موقعه على الخادم (المشاركة مطفأة افتراضياً) لا تصله تذكيرات الصلاة من الخادم.
- كل إرسال يُسجَّل قبل الإرسال في `reminder_pushes` بمفتاح (المستخدم، المهمة، الدقيقة)، فلا يُرسل التذكير مرتين ولو تكرر التشغيل، ولا يصل للمهمة إشعاران في الدقيقة نفسها. السجلات أقدم من ٣٠ يوماً تُحذف. الفشل المؤقت لا يُعاد (مرة واحدة على الأكثر).

حدود معروفة:

- التطبيق يجدول أقرب ٦٠ إشعاراً فقط. من عنده أكثر من ٦٠ في أربعة عشر يوماً (خمس مهام يومية مرتبطة بالصلوات مثلاً) ولم يفتح التطبيق مدة أطول من نافذته الفعلية قد يفوته بعضها. الحل اللاحق أن يرسل التطبيق آخر وقت جدوله فعلاً.
- إذا فتح المستخدم التطبيق بين وقت التذكير وتشغيل الـ Cron (أقل من ٥ دقائق) بعد غياب طويل، فقد يُعدّ الجهاز مغطياً ولا يُرسل الإشعار، والمستخدم حينها داخل التطبيق.
- وقت التعديل من ساعة الجهاز الذي عدّل؛ فرق الساعة قد يسبب إشعاراً مكرراً نادراً، وهو أهون من فواته.
- تذكيرات الموقع لا تُرسل من الخادم.

### الإشعار

- العنوان اسم المشروع، أو «زمام» لمهام الصندوق، والنص عنوان المهمة. لا رموز تعبيرية.
- `aps.category = "zimam.task"` فيظهر زرّا «إنجاز» و«تأجيل ساعة» كما في الإشعار المحلي، و`taskId` في الحمولة ليفتح التطبيق المهمة، و`thread-id` معرّف المشروع أو `inbox`.
- الترويسات: `apns-push-type: alert`، و`apns-topic` معرّف الحزمة المسجَّل، و`apns-priority: 10`، و`apns-expiration` بعد وقت التذكير بيوم.

### المرسل

`src/push/apns.ts`: مصادقة بالرمز. رمز المزوّد JWT بـ ES256، يوقَّع بمفتاح APNs (`APNS_KEY_ID` و`APNS_PRIVATE_KEY` سرّان) ومعرّف الفريق (`APNS_TEAM_ID` في `vars`). يصلح الرمز ساعة، ويُجدَّد بعد ٥٠ دقيقة، ويُحفظ في جدول `apns_tokens` مع ذاكرة في كل isolate، لأن Apple ترفض تجديده أكثر من مرة كل ٢٠ دقيقة وكل تشغيل للـ Cron قد يكون في isolate جديد. المفتاح نفسه لا يُحفظ إلا في الأسرار.

- `410 Unregistered` و`400 BadDeviceToken` و`400 DeviceTokenNotForTopic` تحذف الجهاز.
- `403 ExpiredProviderToken` يوقّع رمزاً جديداً ويعيد المحاولة مرة.
- بلا الأسرار لا يُرسل شيء ويُكتب تحذير في السجل.
- يُمرَّر المرسل عبر `Deps.push`، والاختبارات تستعمل مرسلاً وهمياً (`test/push.test.ts`).

الإعداد (المفتاح وتفعيل Push Notifications) في `docs/setup.md`. ثم من داخل `api/`:

```sh
npx wrangler secret put APNS_KEY_ID
npx wrangler secret put APNS_PRIVATE_KEY    # محتوى ملف .p8 كاملاً
npx wrangler d1 migrations apply zimam --remote   # الجداول devices وreminder_pushes وapns_tokens
```

## المزامنة اللحظية

طبقة تنبيه فوق المزامنة لا بديل عنها: سجل التغييرات (`changes`) والمؤشر هما المرجع، والخادم يقول للأجهزة المفتوحة «اسحب الآن» فقط.

- لكل مستخدم كائن Durable Object من الصنف `UserChannel` (`src/realtime/channel.ts`) باسم معرّفه، يحمل مقابس WebSocket لكل أجهزته ونوافذه بواجهة الإسبات (Hibernation): يخرج الكائن من الذاكرة بين الرسائل وتبقى المقابس مفتوحة.
- الرسالة الوحيدة من الخادم `{"type":"changed","seq":N}`، و`N` أحدث سجل تغيير يراه المستخدم، ولا بيانات فيها. يسحب الجهاز إن كان `N` بعد مؤشره، ويتجاهلها إن لم يكن.
- يرسل العميل `ping` كل ٣٠ ثانية فيجيبه الخادم `pong` دون إيقاظ الكائن (`setWebSocketAutoResponse`).

### الاتصال

| المسار | ما يفعله |
| --- | --- |
| `POST /v1/realtime/ticket` | تذكرة `{ ticket, expiresAt }` تصلح مرة واحدة ولمدة ٦٠ ثانية، للمتصفح لأنه لا يرسل ترويسة `Authorization` مع WebSocket. يُحفظ تجزيئها فقط في `realtime_tickets` مع جلستها، فتسقط بتسجيل الخروج |
| `GET /v1/realtime` | ترقية إلى WebSocket، بـ `?ticket=` أو بـ `Authorization: Bearer` (تطبيق أبل). 401 دون أحدهما، و426 لطلب ليس ترقية، و403 لأصل (`Origin`) خارج `ALLOWED_ORIGINS` |

- تسجيل الخروج يغلق مقابس تلك الجلسة، وحذف الحساب يغلق كل مقابس المستخدم، بالرمز `4001`، فلا يعيد العميل الاتصال.
- حتى ٣٢ مقبساً لكل مستخدم، ويُغلق الأقدم إن زادت.

### متى يُرسل التنبيه

من نقطة واحدة: `requireUser` (`src/middleware.ts`). في كل طلب كتابة (غير `GET`) يقرأ آخر `seq` في سجل التغييرات مع التحقق من الجلسة في الطلب نفسه إلى D1، وبعد الرد (`waitUntil`) يجمع ما كُتب بعده (`notifyChangesSince` في `src/realtime/notify.ts`): أعضاء المشروع لكل سجل موجّه لمشروع، وصاحب كل سجل موجّه لمستخدم، وهو الجمهور نفسه الذي يقرؤه `GET /v1/sync`. ويرسل لكل واحد أحدث `seq` يخصه. فيشمل المزامنة وREST والأعضاء والدعوات وحذف الحساب دون استدعاء في كل مسار، و`ZimamService` يفعل مثله لكتابات Claude وChatGPT. ومستهلك طابور الاستيراد خارج `requireUser`، فيستدعي `latestSeq` قبل كل دفعة و`notifyChangesSince` بعدها (`queue` في `src/index.ts`)، وكذلك أي كتابة جديدة خارجه.

- لا يُستثنى الكاتب: أجهزته الأخرى تحتاج التنبيه، والجهاز الذي سحب يتجاهل `seq` عنده.
- العضوية تُقرأ بعد الكتابة، فالعضو المُزال لا يصله إلا ما وُجّه له.
- قد يصل تنبيه زائد إن كتب غيره في اللحظة نفسها، ولا يضر.
- فشل التنبيه لا يُفشل الكتابة ولا يبطئها: يجري بعد الرد، وأخطاؤه تُكتب في السجل فقط. والعميل الذي فاته تنبيه يسحب عند إعادة الاتصال وعند العودة إلى التطبيق.
- يُمرَّر عبر `Deps.realtime`، فتستعمل الاختبارات منبّهاً وهمياً أو الكائن الحقيقي (`test/realtime.test.ts`).

### العملاء

- **الويب** (`web/public/app/lib/realtime.js`): يتصل بعد الدخول بتذكرة، ويعيد تحميل العرض بعد ٠٫٨ ثانية من آخر تنبيه. ويؤجله ما دامت نافذة حوار مفتوحة، أو مهمة تغادر قائمتها، أو التركيز بلوحة المفاتيح داخل العرض. يعيد الاتصال بتراجع من ثانية إلى دقيقة، ويغلق المقبس بعد ٣٠ ثانية من إخفاء التبويب، ويعود مع تحديث عند ظهوره.
- **تطبيق أبل** (`apple/Zimam/Sync/RealtimeChannel.swift`): `URLSessionWebSocketTask` بترويسة الجلسة، مفتوح ما دام التطبيق نشطاً ومسجّلاً، ويُغلق في الخلفية وعند الخروج. تنبيه `seq` بعد المؤشر يشغّل مزامنة، وكذلك العودة بعد انقطاع.

### النشر

في `wrangler.jsonc` ربط `USER_CHANNEL` وهجرة الصنف `v1` (`new_sqlite_classes`)، فينشئه النشر العادي. ثم من داخل `api/`:

```sh
npx wrangler d1 migrations apply zimam --remote   # جدول realtime_tickets
```

## الاستيراد

ينقل المستخدم مهامه من تطبيق آخر دفعة واحدة. الطلب ينشئ مهمة استيراد في جدول `import_jobs` ويضعها في الطابور `zimam-imports`، ومستهلك الطابور في الـ Worker نفسه (`queue()` في `src/index.ts`) يقرأ المصدر ويكتب السجلات عبر الـ Mutator، فلكل سجل سجل تغيير وتصل الأجهزة بالمزامنة كالعادة. إنشاء الطابورين ومخزن R2 قبل النشر في `docs/setup.md` («الاستيراد»).

### المسارات

| المسار | ما يفعله |
| --- | --- |
| `GET /v1/imports/sources` | المصادر `{ maxFileBytes, sources: [{ id, label, input: "file" \| "token", extensions? }] }` |
| `POST /v1/imports` | ملف: `multipart/form-data` بالحقلين `source` و`file`. رمز: JSON `{ source: "todoist-api", token }`. يرجع 202 `{ job }` |
| `GET /v1/imports` | آخر عشرين استيراداً للمستخدم `{ jobs }`، الأحدث أولاً |
| `GET /v1/imports/:id` | `{ job }`، و404 لاستيراد مستخدم آخر |

```json
{
  "id": "…", "source": "todoist-csv", "status": "running", "fileName": "زواج.csv",
  "progress": { "processed": 50, "total": 121 },
  "counts": { "created": 48, "updated": 0, "unchanged": 0, "skipped": 0, "failed": 2,
              "byEntity": { "project": { "created": 1, … }, "task": { … } } },
  "warnings": ["مهام لم يُفهم تكرارها، فحُفظ نصه في ملاحظاتها: ٣"],
  "errors": [{ "entity": "task", "title": "…", "message": "تعذّر استيراد المهمة «…»: …" }],
  "error": null, "createdAt": 0, "updatedAt": 0, "finishedAt": null
}
```

- الحالات: `queued` ثم `running` ثم `done` أو `failed`. عند الفشل `error: { code, message }`: الرمز ثابت بالإنجليزية والنص عربي يعرضه التطبيق كما هو (`invalid_file`، `invalid_encoding`، `token_rejected`، `nothing_to_import`، `too_many_items`، `source_unavailable`، `internal`…). ما استُورد قبل الفشل يبقى، وإعادة الاستيراد تكمل الباقي دون تكرار.
- `created` جديد، و`updated` تغيّر في المصدر فحُدّث، و`unchanged` مطابق فلم يُكتب، و`skipped` عُدّل أو حُذف في زمام بعد آخر استيراد فبقيت نسخة زمام، و`failed` رفضه الـ Mutator (السبب في `errors`، بحد خمسين).
- `warnings` ما لم يُنقل كما هو: تكرار أو موعد لم يُفهم فحُفظ نصه في ملاحظات المهمة، وملاحظات TickTick، وأقسام صندوق الوارد، والمهام بلا عنوان.
- الأخطاء قبل البدء: `400 invalid_source` أو `invalid_file_type` أو `empty_file` أو `invalid`، و`413 file_too_large` (الحد ٥ ميغابايت، `MAX_UPLOAD_BYTES`)، و`409 import_in_progress` (استيراد واحد في الوقت نفسه لكل مستخدم؛ المهمة التي لم تتحرك ساعة لا تمنع غيرها)، و`503 import_unavailable` إن رفض الطابور الرسالة.

### المصادر

| `source` | المدخل | ما يُنقل |
| --- | --- | --- |
| `todoist-csv` | ملف CSV من Todoist: «قوالب ← تصدير كقالب» | مشروع واحد باسم الملف، وأقسامه، ومهامه ومهامها الفرعية (`INDENT`)، وصفوف `note` في الملاحظات، والوسوم المكتوبة في العنوان (`@وسم`). المهام المنجزة ليست في هذا التصدير |
| `todoist-api` | رمز Todoist الشخصي: «الإعدادات ← التكاملات ← المطوّر» | المشاريع (المشروع الأب بلا مهام يصير مجلداً، وصندوق Todoist يصير صندوق زمام)، والأقسام، والمهام المفتوحة، والوسوم، والموعد النهائي. يقرأ REST API v2، ويتبع الصفحات (`next_cursor`) إن رجعت بصيغة API v1 |
| `ticktick-csv` | النسخة الاحتياطية من TickTick: «الإعدادات ← الحساب ← النسخ الاحتياطي» | المجلدات والقوائم (`Inbox` صندوق زمام) وأعمدة الكانبان، والمهام والفرعية، والوسوم، والتكرار (RRULE)، والتذكيرات، والمنجزة. ملاحظات TickTick (`Kind = NOTE`) لا تُنقل |
| `google-tasks` | ملف `Tasks.json` من Google Takeout | كل قائمة مشروع، والمهام والفرعية بترتيب Google، والمنجزة، والروابط في الملاحظات. المحذوفة لا تُنقل |
| `csv` | أي CSV صفّه الأول أسماء الأعمدة | الأعمدة بالعربية أو الإنجليزية (`COLUMNS` في `sources/generic-csv.ts`): العنوان (إلزامي)، الملاحظات، التاريخ، الوقت، المشروع، القسم، الأولوية، الحالة، الوسوم. الفاصل فاصلة أو فاصلة منقوطة أو Tab |

قواعد مشتركة:

- **الأولوية:** Todoist ٤ (p1) عالية ٣، و٣ متوسطة، و٢ منخفضة، و١ بلا. TickTick ٥ و٣ و١ و٠. وفي CSV العام: «عالية/متوسطة/منخفضة» أو high/medium/low أو p1–p4 أو ٠–٣ بمقياس زمام.
- **التواريخ:** زمام يحفظ الموعد بساعة المستخدم المحلية (`dueDate` و`dueTime`). التاريخ بلا منطقة زمنية يُقرأ كما كُتب في منطقة المستخدم (`settings.timeZone`). والوقت المطلق (`Z` أو إزاحة) يُحوَّل إليها، إلا TickTick فيُقرأ بمنطقة المهمة نفسها (عمود `Timezone`) لأنها ما رآه المستخدم هناك. وGoogle يحفظ التاريخ وحده فيُؤخذ كما هو. في CSV: ISO، واليوم أولاً (`20/10/2026`، والشهر أولاً إن لم يصلح غيره)، وأسماء الأشهر، والأرقام الهندية، والهجري بأم القرى إذا كانت السنة بين ١٣٠٠ و١٦٠٠ (`١٤٤٨/٠٥/٠١ هـ`). التواريخ النسبية («tomorrow») لا تُخمَّن: تُحفظ نصاً في الملاحظات.
- **التكرار:** RRULE من TickTick كما هو (بعد حذف ما ليس من RFC 5545). وعبارات Todoist الإنجليزية الشائعة («every day»، «every 2 weeks»، «every monday, thursday») تُحوَّل إذا كان معها تاريخ بداية، وما سواها يُحفظ نصاً في الملاحظات.
- **الإنجاز:** المهمة منجزة فقط إذا قال المصدر ذلك (TickTick الحالة ١ أو ٢، و-١ «لن تُنجز» مع سطر يقول ذلك في الملاحظات، وGoogle `completed`، والعمود «الحالة» في CSV)، مع وقت الإنجاز إن وُجد. لا تُسقط المهام القديمة ولا تُنقل منجزة دون علامة.
- **التذكيرات:** من TickTick فقط، تذكيرات وقت على المهام المفتوحة غير المتكررة (تذكير بوقت ثابت لا يتبع التكرار). Todoist REST لا يعطي التذكيرات.
- **الحدود:** العنوان الأطول من ٥٠٠ حرف يُقصّ ويُحفظ كاملاً في الملاحظات، وحدود الوسوم والأسماء كما في `schemas.ts`. ولا يتجاوز الاستيراد الواحد ٢٠٠٠٠ عنصر (`MAX_ITEMS`).
- **الترميز:** UTF-8 (مع BOM أو دونه)، وUTF-16 بـ BOM، وWindows-1256 الذي يحفظ به Excel العربي ملفات CSV.

### عدم التكرار

كل سجل مستورد يُربط بمصدره في `external_refs` (`source`، والمعرّف الخارجي ← معرّف زمام)، فإعادة استيراد البيانات نفسها تحدّث ولا تكرر:

- المعرّف الخارجي معرّف المزوّد نفسه حين يوجد (`task:7498225981`)، فيصلح للمزامنة الثنائية لاحقاً. ملفات CSV بلا معرّفات، فيُبنى المفتاح من الأسماء والمكان وترتيب التكرار (المشروع، القسم، الأب، العنوان، والمرة)، ولا يُحفظ إلا تجزيئه SHA-256. لذلك تغيير عنوان مهمة في ملف CSV ثم استيراده ينشئ مهمة جديدة.
- السجل الذي عُدّل في زمام بعد آخر استيراد (`updated_at` أحدث من `synced_at`) أو حُذف فيه لا يُكتب فوقه، وما فيه لا يعود. وما يتبعه (مهام مشروع محذوف، فرعية مهمة محذوفة) يُترك كذلك.
- السجل المطابق لا يُكتب، فإعادة الملف نفسه لا تضيف سجلات تغيير.
- الحقول التي لا يعرفها المصدر (الربط بالصلاة، والإسناد) تبقى كما وضعها المستخدم.
- تُكتب الروابط قبل السجلات، فالدفعة التي يُعاد تشغيلها بعد تعطّل تجد المعرّفات نفسها ولا تنسخ.

### الطابور

- أول رسالة `{ jobId, cursor: 0, token? }` تقرأ المصدر مرة واحدة (الملف من R2 أو واجهة Todoist)، وتحفظ السجلات المحلَّلة في R2 (`parsed/<id>.json`) وتحذف الملف المرفوع (`uploads/<id>`)، ثم تكتب أول دفعة.
- كل رسالة تكتب `CHUNK_SIZE` (٥٠) عنصراً ثم ترسل رسالة الدفعة التالية وتحفظ التقدم (`processed`). الدفعة الصغيرة تبقي استعلامات D1 في التشغيل الواحد تحت الحد (١٠٠٠ في الخطة المدفوعة)، و`max_batch_size: 1` رسالة واحدة في كل تشغيل.
- رسالة لا يطابق مؤشرها `processed` مكررة فتُترك، أو سابقة لحفظ التقدم فتنتظر. وقفل قصير (`lease_until`، دقيقتان) يمنع مستهلكين من الدفعة نفسها.
- الخطأ المؤقت (Todoist ‏429 أو 5xx أو الشبكة أو D1) يُعاد بعد ١٠ ثم ٣٠ ثم ٩٠ ثانية، أو بعد `Retry-After`. وبعد ثلاث إعادات (`max_retries`) تفشل المهمة برسالة عربية. والخطأ الدائم (ملف خاطئ، رمز مرفوض) يفشلها فوراً. وما تعطّل حتى تجاوز الإعادات يصل إلى `zimam-imports-dlq`، ومستهلكه يفشل المهمة.
- عند انتهاء المهمة، نجاحاً أو فشلاً، تُحذف ملفاتها من R2. وحذف الحساب يحذف مهامه، ورسالتها التالية تحذف ملفاتها.

### الأمان

- رمز المزوّد الذي يلصقه المستخدم يمر في أول رسالة من الطابور فقط، ولا يُحفظ في D1 ولا R2، ولا يحتاجه ما بعد القراءة الأولى. الطابور يحفظ الرسالة مشفّرة حتى تُستهلك، ومدة الاحتفاظ يوم واحد. اخترنا ذلك بدل تشفيره بسر `IMPORT_KEY` لأنه لا يُستعمل إلا مرة.
- السجلات لا تكتب رموزاً ولا محتوى ملفات ولا عناوين مهام: معرّف المهمة والدفعة والمحاولة، واسم الخطأ أو مسار المزوّد وحالة HTTP فقط.
- الملفات في R2 مؤقتة، وقاعدة الحذف بعد ٧ أيام شبكة أمان لما لم يُحذف.
- الاستيراد يكتب بصلاحيات المستخدم عبر الـ Mutator نفسه، فلا يصل إلى ما لا يصل إليه التطبيق.

### إضافة مصدر

المصدر يحقق الواجهة `Source` في `src/imports/source.ts`: `FileSource` (`parse(text, ctx)` دالة نقية) أو `TokenSource` (`load(token, ctx)` يقرأ من المزوّد)، ويرجع `ImportBundle` (`src/imports/model.ts`)، ثم يُسجَّل في `src/imports/sources/index.ts`. لا يتغيّر المسار ولا الطابور ولا المستورد. مصادر OAuth (Trello وAsana وNotion وMicrosoft To Do) ستكون `TokenSource` بـ `input: "oauth"` بعد أن يجري التطبيق تدفق OAuth ويرسل الرمز بالطريقة نفسها. وتذكيرات أبل وMicrosoft To Do تُستورد أفضل على الجهاز.

الاختبارات: `test/import-parsers.test.ts` لكل محلّل على ملفات حقيقية الشكل في `test/fixtures/imports/`، و`test/imports.test.ts` للمسارات والطابور (طابور وهمي عبر `Deps.imports`، وR2 من Miniflare).

الواجهة: في التطبيق «الإعدادات» ← «استيراد المهام» (`apple/Zimam/Import/`، وأنواعه وطلباته في `ZimamKit/Imports.swift` و`APIClient+Imports.swift`)، وفي الويب `#/import` (`web/public/app/import-view.js`). كلاهما يرفع الملف أو يرسل الرمز مرة واحدة، ثم يسأل `GET /v1/imports/:id` كل ثانية ونصف حتى ينتهي ويعرض الأعداد والتحذيرات والأخطاء، ثم يزامن. وتذكيرات أبل تُستورد على الجهاز عبر EventKit (`AppleRemindersImport` في ZimamKit): كل قائمة مشروع، وتُحفظ روابط ما استُورد (`calendarItemExternalIdentifier` ← معرّف المهمة) في `UserDefaults` لكل حساب، فلا تتكرر.

## لم يُبنَ بعد

- إرسال `authorizationCode` من موقع الويب: Sign in with Apple JS يعطيه أيضاً، لكن استبداله يحتاج `redirect_uri` نفسه الذي طُلب به، والخادم لا يرسله بعد.
- حصص المساعد بحسب الاشتراك (الحد الآن واحد للجميع).
- مصادر الاستيراد بـ OAuth (Trello وAsana وNotion وMicrosoft To Do) (انظر «الاستيراد»).
- إشعارات الخادم لتذكيرات الموقع، ولما يتجاوز حد الستين إشعاراً داخل نافذة الأربعة عشر يوماً (انظر «إشعارات الخادم»).
